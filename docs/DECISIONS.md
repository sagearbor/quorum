[2026-05-12] | Pydantic AI as the provider implementation layer (all four providers — Azure, OpenAI, Anthropic, local/Ollama — wrapped as Pydantic AI Agents behind LLMProvider) | The hand-rolled provider code had GPT-5 vs reasoning-model branching, a broken Anthropic embed() path, and was diverging from upstream every quarter. [2026-05-12] | A2A protocol via Linux Foundation `a2a-sdk` 1.0.x — per-role `.well-known/agent-card.json` + `/message:send` endpoints on the same FastAPI host, with `agent_endpoints` rows pointing at the same host today | We need agent-to-agent communication for the expo demo and want to truthfully claim "A2A 1.0" on the booth signage. The official SDK gives us SendMessageRequest/Response, AgentCard, and Task protobuf types with the correct camelCase JSON wire format. One host now, multi-host later — switching only requires updating URLs in the `agent_endpoints` registry rows. `tasks/send` is kept as an alias for clients pinned to the pre-1.0 draft. | Hand-roll our own JSON envelope (rejected — won't be standards-compliant, can't claim A2A 1.0), use Azure AI Agents SDK (rejected — vendor lock-in, doesn't speak A2A), embed inside the existing `/contribute` route (rejected — conflates the human and agent dispatch paths)

[2026-05-12] | Magentic-One-style `OrchestratorAgent` (Pydantic AI typed output) replaces `random.choice` speaker election | Random speaker election produced two failure modes — topic drift (the next speaker had nothing to say about what was just said) and monopolies (the same role got picked 3 times in a row). The orchestrator scores candidates by relevance + anti-monopoly and returns `{next_role_id, narration, reason}`; the narration is the one-sentence rationale the avatar speaks while the role-agent thinks. Fallback to `antimonopoly_random_pick()` when the LLM is down so the loop never stalls. | Round-robin (rejected — ignores topic relevance entirely; the safety monitor speaks on a budget topic), pure unstructured LLM pick (rejected — no anti-monopoly guarantee, easy for the LLM to fixate)

[2026-05-12] | `agent_endpoints` registry as a DB-backed routing table (one row per `role_id` with a `url` column) replaces the process-local `_agent_registry` dict | The old in-memory dict lost state on every uvicorn restart and couldn't be queried from any process other than the FastAPI worker that created the role. Today all rows point at the same FastAPI host, but the contract is "change one row to split agents across hosts tomorrow" — the A2A client already reads URLs from this table, so multi-host is a config change, not a code change. `realtime` is enabled so dashboards can surface live agent presence. | Static config file (rejected — needs a redeploy to change), DNS / Consul / k8s service discovery (rejected — overkill for a single-host demo and adds operational complexity), keep the in-memory dict (rejected — already proven to break across workers)

[2026-05-13] | Per-process Python dicts cannot be the source of truth for autonomy loops; promote to `autonomy_loop_state` table with worker-id leases. Reclaim policy is opt-in (`AUTONOMY_LOOP_RECLAIM_ORPHANS`). | The legacy `_active_loops: dict[quorum_id, asyncio.Task]` in `apps/api/autonomy_loop.py` had two failure modes: (1) on uvicorn restart, every quorum with `autonomy_level > 0` silently stopped because the dict was empty — no resume, no alarm; (2) with `workers > 1`, each worker had its OWN dict, so two workers would happily run the same loop and double-dispatch every round. The fix moves the registry to a Supabase table. Each loop iteration UPSERTs a row keyed by `quorum_id` carrying `worker_id = ${HOSTNAME}:${PID}`, bumps `heartbeat_at`, and exits cleanly when a CAS check (`.eq("worker_id", _worker_id())`) sees its lease was taken. Reclaim of rows older than 60s is opt-in via `AUTONOMY_LOOP_RECLAIM_ORPHANS=true`: operators in multi-worker deploys keep it off (a transient slow heartbeat shouldn't trigger a takeover); single-worker dev/expo deploys turn it on so a uvicorn restart resumes ticking. The in-process dict is retained ONLY as a handle map so each worker can `.cancel()` its own `asyncio.Task` — it is NEVER consulted to answer "is this loop running?". | Global `multiprocessing.Manager` dict (rejected — adds an IPC dependency, doesn't survive restart, still per-host), Redis (rejected — adds a runtime dependency the rest of the stack doesn't need; DB is already a hard dep and gives us free RLS, realtime, and FK cascade on quorum delete), keep the dict and document the multi-worker hazard (rejected — already in production and has caused observable double-dispatch in autonomy_level=1.0 runs)

[2026-05-13] | `A2AClient._agent_registry` dict is demoted to a test-only injection map; `agent_endpoints` table fronted by a 60s per-process TTL cache becomes the source of truth | The dict was the only routing table for A2A dispatches in production, but suffered the same per-worker isolation as `_active_loops`. The fix: lookups go DB-first through a tiny `dict[role_id, (url, expires_at)]` cache. TTL is 60s — short enough that re-registering an endpoint in dev is visible within a minute, long enough that an autonomy loop dispatching every 3s gets ~20 cached reads between DB hits. Negative results are NOT cached so a role registered after a failed lookup is visible immediately. Test fixtures continue to call `register_agent()` for unit-test ergonomics; that path now also invalidates the cache so the override takes effect right away. | Read-through with no TTL (rejected — re-registration requires an explicit invalidation call from every caller; brittle), full DB hit on every dispatch (rejected — autonomy_level=1.0 fires these every 3s; that's 50k+ extra DB queries/hr per quorum), Redis as a shared cache (rejected — same as autonomy loop above: adds a dependency we don't need)

[2026-05-13] | `coordination.factory.get_coordination_backend` uses `@functools.lru_cache(maxsize=1)` rather than a module-level `_backend` global | The lazy-singleton pattern (`global _backend; if _backend is not None: return _backend`) is correct but easy to misread as "this should be a DB lookup like the others". Making the cache explicit via `lru_cache` documents the choice: backend construction is intentionally per-process. Backends carry no shared state that matters across workers (just config + an httpx client), so each worker having its own is the right design. The decorator also exposes `.cache_clear()` for tests that monkey-patch `COORDINATION_BACKEND`. | DB-backed instance (rejected — backends are not stateful entities; promoting them to the DB would be cargo-cult), `multiprocessing.Manager`-shared instance (rejected — backends hold httpx clients that aren't picklable), no caching (rejected — re-instantiating the backend on every call adds httpx setup cost we don't need)
